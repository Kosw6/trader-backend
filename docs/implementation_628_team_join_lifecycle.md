# 628: 팀 재가입 이력과 가입 요청이 있는 팀 삭제

후속 운영 적용·실제 API 검증은 [629 배포 기록](implementation_629_team_lifecycle_release.md)을 따른다. 아래는 운영 적용 전 로컬 구현 기록이다.

2026-10-29 KST. 627 실제 검사에서 남았던 팀 재가입·팀 삭제 결함을 보완했다. **코드와 격리된 로컬 PostgreSQL 검증 완료, 운영 반영 전**이다. AWS와 GPU를 기동하지 않았다.

## 동작 변경

- 기존 `UNIQUE(team_id, requester_id)`는 과거 APPROVED/REJECTED 요청이 있으면 새 가입 요청까지 막았다. V049는 이를 `status='PENDING'`에만 적용하는 부분 유일 인덱스로 바꾼다.
- 재가입은 새 JoinRequest와 새 ID를 만든다. 과거 요청은 수정·삭제하지 않고 보존한다. 예전 승인 버튼을 다시 눌러도 새 요청이 승인되거나 탈퇴자가 다시 가입되지 않는다.
- 이미 팀원이면 기존 거부 동작을 유지한다. PENDING 요청이 있으면 추가 요청/알림을 만들지 않는다. 승인·거절 처리는 기존 소유자 권한 검사를 유지한다.
- 가입·승인/거절·탈퇴·삭제는 팀을 먼저 잠근다. 승인/거절은 그다음 요청을 잠근다. 동시 재가입과 팀 삭제가 서로 다른 잠금 순서를 사용하지 않게 맞췄다.
- 팀 삭제는 같은 트랜잭션에서 그 팀의 모든 가입 요청을 먼저 정리하고 팀을 삭제한다. 다른 팀 요청에는 적용하지 않는다. 팀 자체를 삭제할 때 해당 팀의 가입 요청도 삭제하는 정책이다. 재가입 때는 과거 이력을 삭제하지 않는다.

## 검증

Gradle 오프라인 회귀 테스트 **44개, 실패/오류/건너뜀 0**:

| 테스트 | 개수 |
|---|---:|
| TeamServiceTest | 12 |
| TeamJoinDecisionTest | 13 |
| TeamExitTransactionTest | 2 |
| TeamDomainTest / UserTeamDomainTest | 12 |
| TeamJoinLifecycleTest (신규) | 2 |
| TeamJoinHistoryPostgresTest (신규) | 3 |

새 테스트는 새 요청과 과거 승인 ID의 분리, 과거 승인 재시도 시 새 요청 PENDING 유지, 팀 잠금→요청 삭제→팀 삭제 순서를 검사한다.

실제 로컬 PostgreSQL 17의 전용 무작위 스키마에서 V049를 실행했다. 이전 승인/거절 행 보존, 새 ID 발급, PENDING 중복 거부, 거절 후 재요청, 두 연결의 동시 재가입에서 PENDING 1건 생성, 삭제 후 예외 시 부모와 요청 모두 롤백, 다른 팀 요청 보존을 확인했다. 이는 Spring 서비스 전체의 실제 HTTP/JPA 통합 시험은 아니다. 서비스 경계는 기존 트랜잭션 프록시·서비스 테스트와 함께 검사했다.

테스트 스키마 잔여 0을 확인하고 이번에 시작한 로컬 PostgreSQL을 정상 종료했다. 기존 주가·재무·사용자 운영 자료에는 접근하거나 변경하지 않았다.

증거: 저장소 상위 `output/team-lifecycle628-20261029/verification.json`과 테스트 XML. 코드/SQL SHA도 영수증에 보존했다.

## 운영 적용 순서

1. 새 백엔드 후보와 호환되는 CPU 롤백 아티팩트를 먼저 준비한다. 기존 작업 중인 다른 소스 변경을 함께 배포하지 않도록 변경 범위를 대조한다.
2. 백엔드 가입/승인/탈퇴/삭제 쓰기를 중단한다. 이전 버전이 JPA 스키마 자동 갱신으로 구형 유일 제약을 다시 만들지 않도록, 혼합 버전 기동을 피한다.
3. 운영 `application` 스키마를 지정해 `trader-controller/db/migration/V049__team_join_request_history.sql`을 한 트랜잭션으로 적용한다. 기존 제약과 테이블 존재를 먼저 확인한다. SQL의 3초 잠금 한도에 걸리면 원인을 확인하고 임의 반복 실행하지 않는다. 이 파일은 반복 적용용 SQL이 아니다.
4. JoinRequest의 구형 `@UniqueConstraint` 제거까지 포함한 새 백엔드를 시작한다. 서비스·저장소만 교체하고 엔티티를 구형으로 남기면 안 된다.
5. 합성 계정으로 가입→승인→탈퇴→새 요청→구 요청 재승인→새 요청 승인, 가입 요청을 가진 팀 삭제, 비소유자 거부를 실제 API로 확인하고 합성 자료를 정리한다.

스키마 복구를 위해 과거 이력을 지우거나 구형 `(team_id,requester_id)` 제약을 다시 만들지 않는다. 재가입 이력이 생긴 뒤에는 그 제약이 더 이상 성립하지 않는다. 롤백 후보도 부분 유일 인덱스와 호환되는 엔티티 매핑을 사용해야 한다. 이번 단계에서는 이 운영 변경·배포·실제 HTTP 검증은 실행하지 않았다.
